# 执行耗时分析：自动模式下的「若干轮 × 每轮若干步」

> 问题：在 `--autopilot`（没有人审批、也没有人回答提问）下跑完一个任务 ——
> 若干轮、每轮若干步、直到给出最终回复 —— 这段时间到底花在哪？
>
> 结论：**可行，而且这个项目已经具备做这件事的全部条件**。分析做完了，
> 结论是模型往返主导，程序自身开销每步只有几毫秒。
>
> **本报告的第 7 节 ① 已经落地**（会话落盘从"整份重写"改成"只追加"），
> 所以第 5、6 节现在是**改后**的数字，并附上与改前的对照。
> 改动本身见 `state/store.py` 的模块 docstring。

---

## 1. 结论先行

1. **墙上时间 ≈ Σ模型往返 + Σ工具执行 + 自身开销**。在自动模式下前两项占 **99.8%**
   以上，人等人那两项恒为 0。所以"完成一个任务要多久"这个问题，
   答案的 99.8% 由 provider 和工具决定，**不是这份代码**。

2. 自身开销每步只有几毫秒。**改之前它不是常数**——随会话历史线性变贵，
   整个回合是**步数的平方**（`state/store.py` 每次 checkpoint 整份重写会话，
   而 checkpoint 每步一次）。这个二次项**已经修掉**：落盘改成只追加，
   现在 80 步和 36 步的每步开销一样（2.97ms vs 2.98ms）。

3. 修掉它换来的**不是墙上时间**（在你自己的场景里那是 0.15%），
   而是另外两样更实在的东西：

   | | 改前 | 改后 |
   |---|---:|---:|
   | 80 步那一轮的落盘量 | **863MB** | **21.0MB** |
   | 写入放大 | **41×** | **1.0×** |
   | 该轮"程序自身耗时" | 5.86s | **0.29s** |

   也就是 **SSD 写入量降 41 倍**，以及"会话越长越糟"那条曲线被拉平。

4. **瓶颈换人了。** 修完之后最大的两项变成 `工具阶段`（41%）和 `会话落盘`（47%），
   而**审计写入**从"可忽略"升到了墙上时间的 **28%** —— 其中约三分之二是
   每条事件一次 `open`/`close`（见第 6 节）。这是下一个值得动的地方。

## 2. 方法：两条互补的路

只走一条都会得出片面的结论，所以做了两条，让它们互相印证 / 互相补盲。

| | 数据来源 | 能回答 | 盲区 |
|---|---|---|---|
| **上：审计归因** | 已有的 `.tudouni/logs/*.jsonl` | 真实场景里各项的**实际占比** | 自身开销会被毫秒取整和网络抖动淹没 |
| **下：零延迟基准** | 假模型 + 真 Agent | 自身开销的**精确值与增长曲线** | 不含真实模型延迟 |

上半段的归因口径**不写在脚本里**，而是直接 import `frontends/cli/summarize_time()`
—— 那是 `/status` 那行汇总用的、也是唯一被测试盯着的那一份。所以报告里的数字和
用户在界面上看到的是**同一个算法**，不会出现"分析脚本算一套、产品显示另一套"。

下半段把模型换成零延迟假模型，于是墙上时间里只剩下这份程序自己做的事。
它跑的仍然是**真的** `Agent.run()`、真的工具注册表、真的 pydantic 校验、
真的会话落盘和审计写入 —— 假掉的只有网络那一跳。

复现方式见第 8 节。

## 3. 耗时模型（可以直接套用）

```
T(轮数 R, 每轮步数 S, 每步回灌 C 字节)
    = R·S·(T_model + T_tool)          ← 主项，99.8%
    + T_self(R, S, C)                 ← 本程序的开销
```

`T_self` 拆开（数字全部来自第 5 节的实测，**改后**）：

```
T_self ≈ R · [ 2.5ms           (工具 schema 生成，每轮一次)
             + (S+1) · 1.7ms   (会话落盘：只写新增的那一段)
             + S · 1.0ms       (审计写入，约 6 条事件/步)
             + S · 0.6ms ]     (载荷拼装 + 消息追加 + 重试记账)
```

**每一项现在都是线性的**，所以：

```
T_self ≈ R·S · 3.5ms  +  R · 2.5ms        （整字节回灌换来的那部分见下）
```

改之前落盘那一项是 `S²·C / (2 × 140MB/s)` —— 唯一的非线性项，现在没有了。
它只和"这一步新增了多少字节"有关，和历史多长无关。

### 两个算例

**例一：典型任务（5 轮 × 10 步，每步读一份 64KB 的源码）**

```
模型   50 × 5.5s   = 275s      ← 5.5s 是真实日志里量到的均值，见第 4 节
工具   50 × 1.0s   =  50s
自身   50 × 3.5ms  ≈ 0.18s
                     ─────
                     325.2s      自身占 0.05%
```

**例二：极端形状（1 轮撞满 max_steps=80，每步读 256KB）**

```
模型   80 × 5.5s  = 440s
自身               = 0.29s     自身占 0.07%，写盘 21MB
```

套公式、代入你自己场景的 `R` / `S` / `C`，以及你那条路由上量到的 `T_model`，
就是"完成一个任务要多久"的完整答案。

## 5. 自身开销基准（下：零延迟假模型）

`scripts/perf_selfcost.py` 的全矩阵输出（**改后**）。分段口径是**互不重叠**的
（`模型阶段` / `工具阶段` / `落盘阶段`，`其余` = 墙上时间 − 三段），
所以可以直接相加；`审计写入` 等是嵌套细项，不能和它们相加。

权限裁决实际出现的来路只有 `autopilot` —— 也就是**一次都没问人**，
这正是用户要的那个场景。

> 下表的数字是**一次代表性运行**（每个基线场景取 3 遍的中位数）。
> 在一台笔记本上重跑，绝对值会有 ±20% 的波动 —— 结论（占比和增长形状）
> 不受影响，但别把某个具体毫秒数当成常数。

| 场景 | 轮×步 | 回灌/步 | 墙上时间 | **每步自身** | 模型阶段 | 工具阶段 | 落盘阶段 | 其余 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 基线 | 1×12 | 1KB | 26ms | **1.8ms** | 3.6ms | 13.8ms | 5.0ms | 3.4ms |
| 基线 | 1×36 | 1KB | 79ms | **1.8ms** | 10.8ms | 50.3ms | 13.5ms | 4.0ms |
| 基线 | 1×12 | 64KB | 27ms | **1.8ms** | 3.3ms | 13.1ms | 7.5ms | 3.1ms |
| 基线 | 1×36 | 64KB | 83ms | **1.9ms** | 10.1ms | 44.6ms | 24.0ms | 4.0ms |
| 基线 | 1×12 | 256KB | 45ms | **3.2ms** | 3.9ms | 17.3ms | 20.8ms | 3.2ms |
| 基线 | 1×36 | 256KB | 133ms | **3.0ms** | 11.1ms | 54.4ms | 62.7ms | 4.3ms |

### 5.1 消融：确认每一项的归属

| 场景（同上 1×36 / 256KB） | 墙上时间 | 每步自身 | 结论 |
|---|---:|---:|---|
| 基线 | 133ms | 3.0ms | |
| 无落盘 | 81ms | 1.5ms | 落盘仍是最大单项（47%），但已是线性的 |
| 无审计 | 100ms | 2.1ms | 审计占 28% |
| 无落盘无审计 | **34ms** | **0.2ms** | 地板 |

### 5.2 写入放大：**这是这次改动唯一的观测点**

会话文件现在是只追加的，所以「累计落盘字节 ÷ 最终会话大小」应当逼近 **1×**。

| 场景 | checkpoint 次数 | 累计落盘 | 最终大小 | 放大倍数 |
|---|---:|---:|---:|---:|
| 1×12 / 1KB | 13 | 0.0MB | 0.02MB | **1.0×** |
| 1×36 / 1KB | 37 | 0.1MB | 0.05MB | **1.0×** |
| 1×36 / 64KB | 37 | 2.3MB | 2.34MB | **1.0×** |
| 1×36 / 256KB | 37 | 9.3MB | 9.32MB | **1.0×** |
| 5×6 / 256KB | 35 | 6.7MB | 6.66MB | **1.0×** |

**这个数掉回几十倍就说明落盘退回了整份重写** —— 这是唯一会在功能测试全绿的情况下
悄悄退化的东西，所以 `tests/test_state_store.py` 里专门有两条盯着它
（`test_a_save_writes_only_what_is_new_not_the_whole_history` 和
`test_what_was_already_written_is_never_touched`）。

### 5.3 改前 / 改后对照

| 形状 | 每步自身 | 落盘 | 累计落盘 | 放大 |
|---|---:|---:|---:|---:|
| 1×12 / 1KB | 4.6ms → **1.8ms** | 27.3ms → **5.0ms** | 0.2MB → **0.0MB** | 8.0× → **1.0×** |
| 1×36 / 64KB | 13.3ms → **1.9ms** | 408.6ms → **24.0ms** | 44.6MB → **2.3MB** | 19.0× → **1.0×** |
| 1×36 / 256KB | 36.4ms → **3.0ms** | 1240ms → **62.7ms** | 177.2MB → **9.3MB** | 19.0× → **1.0×** |
| 1×80 / 256KB ※ | 72.4ms → **2.97ms** | 5639ms → **137ms** | 863MB → **21.0MB** | 41.0× → **1.0×** |

※ 80 步那一行是单独测的（不在默认矩阵里），因为默认的 `max_steps` 就是 80。

**最要紧的一行是这个**：改后 80 步的每步开销（2.97ms）和 36 步（2.98ms）**一样**。
改之前它们差 2.4 倍，而那正是二次项的形状。

### 5.4 逐轮：现在是一条平线

同一份会话，后面几轮的起点已经是前面几轮**全部的历史**，所以改前轮耗时逐轮上升：

```
改前  5×6 / 256KB：  67ms → 142ms → 234ms → 290ms → 417ms     （末轮/首轮 = 6.2×）
改后  5×6 / 256KB：  22ms →  22ms →  28ms →  21ms →  23ms     （平的）
```

### 5.5 流式仍然几乎免费

`变体 开流式`（每步 40 块 delta，走完整的 `_DeltaRelay` + sink 路径）：
**3.3ms/步 vs 基线 3.0ms/步** —— 在测量噪声以内。

这条值得单独说，因为流式是这个项目里"代价最大的一个功能取舍"
（`agents/agent.py` 的 `RunCancelled` docstring 里记了三笔代价）。
**那三笔代价里没有"性能"这一笔。**

## 6. 归因：热点在哪个函数上

`cProfile`（1×36 / 256KB，**改后** 0.163s 采样 —— 改前同一个场景是 2.015s）
按 tottime 排序的前几名：

```
ncalls  tottime  cumtime  function
   217    0.030    0.035  {built-in method _io.open}
   324    0.026    0.026  json/encoder.py:205(iterencode)
   180    0.023    0.023  {method 'write' of '_io.TextIOWrapper'}
   217    0.020    0.020  {method '__exit__' of '_io._IOBase'}      ← 关文件
    78    0.011    0.011  {built-in method nt._getfinalpathname}
    37    0.001    0.062  state/store.py:164(save)
   143    0.001    0.049  audit/jsonl.py:35(__call__)
```

改前是 `save()` 一个函数吃掉 **90.7%** 的 CPU；现在最大的单项是
**`open` + `close` 这一对**，而它出现在两个地方：

| | 次数 | cumtime | 每次 | 里面主要是什么 |
|---|---:|---:|---:|---|
| `store.save` | 37 | 62ms | 1.7ms | 写新增的字节（`dumps` + `write`）—— 该花的 |
| `audit/jsonl.py` | 143 | 49ms | **0.34ms** | **约三分之二是 `open`/`close`**，不是数据 |

**这就是第 7 节 ② 的依据**：审计日志每条事件开一次、关一次文件，而一条事件的正文
只有几百字节 —— 开关文件比写它贵得多（实测 `open` ≈ 0.14ms、`close` ≈ 0.09ms）。

`nt._getfinalpathname` 那 78 次来自工具层：`FileSystem.safe_path` 对每个路径调
`.resolve()`。36 步 × 2 次，合计 11ms —— 占比 7%，属于"知道就行"的量级。

> `indent=2` 曾经被怀疑是元凶，实测**不是**：这份载荷的 99% 是长字符串，
> 而缩进只作用在容器上。真正的成本曾经是**体积 × 次数**，而次数那一半已经修掉了。

## 7. 瓶颈清单与建议（按性价比排序）

### ① 会话落盘：已改成「增量追加」 ✅

见 `state/store.py` 的模块 docstring（为什么、格式是什么、崩溃安全怎么变），
以及 `tests/test_state_store.py` 里那一节专门盯着"只追加"的测试。

写放大 **41× → 1.0×**，二次项消失，80 步那一轮的自身开销 **5.86s → 0.29s**。

### ② 审计写入：复用文件句柄（现在最值得做的一个）

现状：`audit/jsonl.py` 每条事件一次 `open`/`write`/`close`。实测一步约 6 条事件，
**占改后自身开销的 28%**，而 cProfile 显示其中约三分之二是 `open`/`close` 本身。

`jsonl.py` 的 docstring 说得很清楚，这是**有意为之**的（写完即落盘，进程随时被杀
不丢事件）。所以建议**不是**改成缓冲，而是改成**常驻句柄 + 每条 `flush()`**：
`flush` 比 `open`/`close` 便宜一个量级，而"每条都已经交给操作系统"这个性质不变。

**真正的风险只有一个**，而且它现在也存在：进程被 `kill -9` 时，已 `flush` 但未
`fsync` 的数据仍在页缓存里 —— 但那和现在 `close()` 的行为是一回事（`close` 也不 `fsync`）。
代价是句柄的生命周期要有主（谁来关、会话切换时怎么办），这是这个方案唯一需要设计的地方。

预计收益：自身开销再降约 20~25%。

### ③ 工具 schema 生成：按 Tool 缓存（每轮约 2.5ms）

`Tool.parameters` 每次都调 `args_model.model_json_schema()`，而 schema 对一个
Tool 实例是**不变的**。`ToolRegistry.schemas()` 已经只在每轮开头调一次了，
所以这是固定成本而不是热路径 —— 但在"很多短回合"的形状下会累积
（`多轮 5×6` 场景里 5 轮合计 12.6ms）。

改法：在 `Tool` 上缓存，或者改成 `functools.cached_property`。
`Tool` 是 `frozen=True` 的 dataclass，所以需要一个非字段的缓存槽。

### ④ 不值得优化的（已经量过，明确排除）

* **载荷尾部拼装**（`_status_note`，每步现拼任务列表 + 步数预算）：**0.1ms/轮**；
* **流式**（`_DeltaRelay` + sink）：**噪声以内**（5.5 节）；
* **消息列表复制**（`[*messages, note]`）：指针复制，未进入热点前列；
* **权限关卡**：autopilot 下是一次集合查找，未进入热点前列；
* **`indent=2`**：见第 6 节，**不是**问题；
* **`FileSystem.safe_path` 的 `.resolve()`**：占 7%，属于"知道就行"。

## 8. 怎么复现

两个脚本都在 `scripts/` 下，只依赖项目自己的 `.venv`。

```powershell
# 上半段：对现有审计日志做归因（和 /status 的汇总同一口径）
.venv\Scripts\python.exe scripts\perf_audit_report.py --out .perf-tmp\audit-report.md

# 下半段：零延迟基准（矩阵 + 消融 + 写入放大）
.venv\Scripts\python.exe scripts\perf_selfcost.py --profile

# 只看某个形状
.venv\Scripts\python.exe scripts\perf_selfcost.py --payload 65536 --steps 12,36 --no-ablation
```

两个脚本都把结果写到 `.perf-tmp/`（已加进 `.gitignore`），
`--keep` 可以保留上一轮的临时数据。

**要看"落盘有没有退回整份重写"，只需要看报告里那张「写入放大」表** ——
它应当恒为 1.0×。**跑之前请确认 `.tudouni/logs/` 里有东西** —— 日志被清空之后
`perf_audit_report.py` 会明确报"没找到审计日志"并以 2 退出（这是有意的，
和 `main.py` 里那些子命令"配置缺失 = 用户得先做点事"是同一条）。

## 9. 这次分析没有覆盖的

诚实列出来，免得被当成"已经全查过了"：

* **真实模型延迟的分布** —— 只有一份会话的 33 个样本（均值 5.5s）。
  要更准的话，`perf_audit_report.py` 已经会把 `model_call` 的
  p50/p90/max 分成功与失败算出来，多攒几份日志再跑一次就行。
* **prompt cache 命中率对延迟的影响** —— 捕获到的那一条首轮调用是
  `cached_tokens 384 / prompt_tokens 4362`（9%），但首轮本来就是冷的。
  日志里有 `cached_tokens` / `miss_tokens`，值得单独拉一条曲线。
* **工具执行本身的优化** —— 4.2 节显示它才是真实任务的大头，
  但那是"少跑几次慢命令"的问题，不属于这次"程序执行耗时"的范围。
* **TUI 前端的渲染开销** —— 基准走的是 Agent 层，没有挂 TUI。
  真实数据里那 14ms/回合的差额有一部分落在那里，但它的量级（十几毫秒）
  决定了不值得为它做一次专门的分析。
* **会话文件的读取端** —— `--list` 会把每个会话整份读一遍（`store.load`），
  50 个 20MB 的会话就是 1GB 的解析。这是**改前改后都一样**的既有问题
  （旧格式也是整份 `json.loads`），所以这次没有退化；但如果会话数量再涨，
  它会是下一个值得量的地方。新格式其实给了它一条出路：`--list` 要的
  `created_at` 住在 head/meta 里，不必把消息也解析出来。
